# Execution Spec Contract v1

This reference defines the executor-facing contract generated by the `execution-spec` Skill.

The executor-facing artifact title is always:

```markdown
# Execution Spec
```

Do not expose the internal contract version in that title.

## Section Order

Use this order and omit optional sections that have no operationally necessary content:

```markdown
# Execution Spec

## Objective

## Scope

## Context
<!-- optional -->

## Requirements

## Acceptance Criteria

## Verification

## Decisions
<!-- optional -->

## Stop Conditions
<!-- optional -->

## Completion Report
```

Required sections:

- `Objective`
- `Scope`
- `Requirements`
- `Acceptance Criteria`
- `Verification`
- `Completion Report`

Optional sections:

- `Context`
- `Decisions`
- `Stop Conditions`

Never emit an empty optional section or a placeholder such as `None`, `N/A`, or `Not applicable`.

## Objective

State one bounded outcome in executor-facing language. Describe what must become true, not how the host discovered the task.

The objective should be specific enough to orient implementation without repeating all requirements or acceptance criteria.

## Scope

Define the task boundary. Include only scope facts that materially constrain execution, such as:

- files, packages, modules, or surfaces that may change;
- protected or explicitly excluded areas;
- whether tests, documentation, migrations, or generated artifacts are in scope;
- relevant compatibility boundaries.

Do not use Scope to expose host authorization mechanics or generic safety policy that belongs to the execution environment rather than the task.

## Context

Use `Context` only for executor-readable working material the executor genuinely needs to inspect while performing the task.

Prefer exact files, directories, issue/spec artifacts, or other materials with a short explanation of why each matters. For example:

```markdown
## Context

Before editing, inspect:

- `src/api/validation.ts` — contains the validation path this task extends.
- `tests/api/validation.test.ts` — establishes the current externally observable behavior.
```

`Context` is not an exhaustive list of every file the executor may inspect. It identifies important working anchors known to the host; ordinary in-scope code navigation remains part of execution.

Do not use `Context` as a shortcut for asking the executor to reconstruct host planning. Do not list meta-context such as Skills, planning notes, architecture handoffs, or repository-wide documentation when the host can compile the relevant rule directly into `Requirements`.

## Requirements

State all resolved instructions the executor must follow to implement the task correctly.

Requirements are task-native. They may originate from user instructions, repository rules, architecture docs, specifications, Skills, research, or host planning decisions, but source provenance normally disappears.

Prefer direct statements such as:

```markdown
- Preserve the existing public API unless the task explicitly requires a breaking change.
- Cover the new behavior with tests that verify externally observable outcomes.
```

Do not write provenance-oriented labels such as `Project constraint:` or `Skill rule:`. State the resolved rule directly.

If a requirement would be ambiguous without a concrete implementation choice, resolve that choice host-side and record it in `Requirements` or `Decisions`.

## Acceptance Criteria

Define observable conditions that establish task completion. Favor externally inspectable behavior, repository state, API shape, artifacts, or test outcomes over vague quality claims.

Each criterion should be independently checkable by a competent reviewer or executor.

## Verification

Specify the checks needed to demonstrate the acceptance criteria, using exact commands when known and useful.

Include only relevant verification. If no automated command applies, state the concrete manual or structural verification the executor should perform rather than inventing a generic test command.

Verification belongs to task completion; it is not a host approval or orchestration workflow.

## Decisions

Use `Decisions` only for task-level choices that the executor must treat as fixed and that are clearer as decisions than ordinary implementation requirements.

Good examples:

```markdown
## Decisions

- Reuse the existing request-validation path rather than introducing a parallel validation pipeline.
- Preserve backward compatibility for the current configuration format.
```

Do not use `Decisions` for:

- planner reasoning;
- alternatives considered;
- discussion history;
- provenance;
- unresolved uncertainty.

Uncertainty that materially affects semantics should be resolved before execution or represented as a narrow stop condition.

## Stop Conditions

Use `Stop Conditions` only when proceeding by guesswork could:

- alter task semantics;
- violate an architectural or scope boundary; or
- make correctness materially unverifiable.

Write concrete triggers. Do not add generic instructions such as `ask if unsure`, `be careful`, or `stop on any ambiguity`.

The host should resolve ordinary ambiguity before emitting the spec.

## Completion Report

Tell the executor what to report after execution. Keep the report operational and concise.

Unless the task requires something more specific, ask for:

- files or artifacts changed;
- verification performed and results;
- any unresolved limitations, blockers, or deliberately uncompleted items.

Do not ask for a reconstruction of planner reasoning, Skill usage, provenance, or the context-compilation process.

## Negative Contract

The executor-facing artifact should normally not contain:

- Skill provenance or instructions to invoke Skills;
- provenance-oriented sections or source-by-source rule classifications;
- context provenance or source-by-source manifests;
- host planning mechanisms unless the task itself directly operates on them;
- planner reasoning, alternatives, or chain-of-thought;
- host tool calls or unavailable-tool workflows;
- host approval mechanics or execution permissions;
- context-compilation reports, manifests, source summaries, or reasoning appendices;
- generic project meta-context that has already been normalized into direct requirements;
- executor-specific launcher mechanics unless they are genuinely part of the task being executed.

## Final Audit

Before delivering the artifact, verify all of the following:

1. The title is exactly `# Execution Spec`.
2. Every required section is present and substantive.
3. Empty optional sections and placeholder values are absent.
4. The executor can understand the task, its boundaries, and its required behavior without reconstructing host-side context. `Context` identifies important working anchors, not an exhaustive read allowlist; additional in-scope code exploration is allowed when needed for implementation or verification.
5. Material conflicts and implementation choices have been resolved rather than delegated back to the executor.
6. Requirements are task-native and do not require the executor to understand their provenance.
7. Stop conditions are narrow and semantically meaningful.
8. The artifact contains one primary task interface, not companion planning or compilation reports.
9. If removing a passage would not change how a competent executor should perform or verify the task, remove it.
