# Current DSH capability audit for the Tempera MVP

Audit date: 2026-09-01 (Asia/Shanghai)

## Baseline and confidence

This audit uses only DeepSeek's official site and the official `deepseek-ai/deepseek-harness` repository. The reproducible release baseline is [`dsh-v0.1.2-alpha.3`](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.3), released 2026-08-31 from commit `dd6322d`; the root package declares `0.1.2-alpha.3`. The official product page and repository still call DSH a developer preview whose APIs will evolve, and the repository explicitly retains a pre-release, no-compatibility-promise stance. Tempera must therefore pin one exact DSH release/commit and enforce compatibility with compile-time and behavioral contract tests rather than depend on an unbounded semver range.

The release note's removal of the optional **SQLite Session persistence** backend does not mean that the separate non-session `dsh-storage-sqlite` backend disappeared: the current storage subsystem still documents JSON and SQLite backends behind `ctx.storage`, with `ctx.storageDomain` as their typed consumer.

## Executive answer

DSH is reusable as Tempera's **composition and execution kernel**, not as its authority store or trust protocol.

Directly reusable foundations are Cordis service composition/lifecycle, named subagent transports, live background-job observation, per-call fail-closed file sandboxing, canonical workspace identity, and low-level durable KV storage. None of those supplies the complete semantics Tempera needs for Task-level CAS plus request idempotency, frozen realizer provenance, Invocation fencing, durable proposal delivery, immutable Candidate integrity, exact Git application, or write-ahead authoritative-effect reconciliation.

Consequently, the MVP should compose Tempera as ordinary DSH/Cordis services and adapt selected DSH providers behind Tempera-owned seams. It must not treat `ctx.jobs`, a DSH Session, `ctx.workspaceRegistry`, or a subagent's successful result as authoritative Task state.

## Reuse and gap matrix

| Area | Current official DSH API and guarantee | Reuse in Tempera | Exact MVP gap / boundary |
| --- | --- | --- | --- |
| Cordis composition | Plugins provide services on `ctx`; `inject` keeps a consumer pending until required services exist. Loss of a required service disposes dependents and reloads them when it returns. Registrations/listeners are reversible effects and `fiber.dispose()` awaits cleanup. Services can be isolated by composition scope. | Mount the Task Manager, DSH adapter, realizer registry, artifact verifier, and workspace/effect providers as normal Cordis plugins/services. Use required injection for correctness-critical dependencies and effect disposal for owned resources. | Cordis lifecycle is process lifecycle, not durable work lifecycle. It does not freeze provider name/version/config/capabilities into an Invocation, preserve a launch across restart, or grant Task authority. Async disposers may run concurrently, so ordered shutdown/recovery must be owned by one Tempera disposer. |
| Durable storage / `storageDomain` | `defineDomain` declares versioned Zod-backed tables. `ctx.storageDomain.open()` routes to a backend. Reads come from authoritative memory; all writes serialize on one per-domain chain. A `put`, `delete`, `update`, or global `set` reaches backend durability before memory/event publication; `update` is an atomic read-modify-write at its chain slot. The backend contract guarantees only that **each single call** is atomic and durable. | Good for durable auxiliary registries and projections. It may support a narrowly tested single-record aggregate envelope where state, journal tail, request result, and version are one value. | There is no public multi-record transaction/unit-of-work API, transactionally appended journal plus current-state mutation across records, explicit expected-version/CAS primitive, or cross-process writer guarantee. The domain chain is process-local. Therefore `storageDomain` is not, by itself, the required authority transaction boundary. Ticket “Choose the first transactional persistence boundary” must either prove the single-envelope design under crash/load or choose a Tempera-owned transactional store (likely a dedicated SQLite adapter) behind a Cordis service. Do not bypass DSH's storage layering by importing a concrete DSH backend as an undocumented database API. |
| Jobs | `ctx.jobs` defines atomic live registration, owner-session access control, `list/get/read/kill/wait`, terminal first-wins settlement, and cleanup. The shipped provider is explicitly `LocalJobRegistry`, process-local; owner/service disposal cancels live work and waits for compliant producers. | Optional observation/control projection for live Invocation activity and model-facing job UI. It can mirror a durable Invocation id in a label/detail, but remains derived telemetry. | Job ids/state do not survive restart; owner disposal actively cancels work; there is no prepared-before-launch record, stable `launchKey`, reattach/idempotent launch, execution generation, proposal disposition, or durable outcome. `ctx.jobs` cannot be the Invocation repository or recovery source. |
| Workflow and schedule execution | `ctx.workflowEngine` runs a model-written, live orchestration script with bounded cancellation/disposal; its durable chat records describe an interrupted prefix, not a resumable workflow. Schedule persists session-local reminder records, but cold Sessions do no work and the enqueue-before-dispatch-record crash window is explicitly at-least-once. | Useful references for lifecycle/error discipline and optional UX, not the Tempera continuation engine. | Neither owns durable semantic Stage continuation or authoritative effects. Tempera must evaluate frozen policy itself; using workflow scripts would create the forbidden executable workflow authority. Schedule's best-effort delivery is insufficient for effect dispatch. |
| Subagents | `ctx.subagents` is a named provider registry. Providers expose `name`, capability flags, context-inheritance description, optional route defaults, `start()`, and optional `prepareContinuable()`. Unsupported requested capabilities fail before start. A one-shot `SubagentRun` exposes id, result, and idempotent dispose. Local runs create child Sessions; continuable children have durable Session ids and cold resume. Provider removal blocks new starts without revoking already accepted runs. | Implement the first coding/evaluation realizer adapter over an explicitly selected named provider. Capture provider name, requested/observed capabilities, route/model options, run/session id, and DSH build in Tempera's frozen `RealizerBinding`. Structured output can carry a constrained proposal payload. | A one-shot run is explicitly not a durable child handle and has no resume/steer. Remote runs have no durable local enumeration. The seam has no caller-supplied idempotent launch key, reconnect contract, immutable provider version/config identity, Task generation fence, durable `proposalRef`, or authoritative acceptance. A continuable child Session is not a Tempera Invocation and must not become Task truth. Completion is only an input proposal to a fenced Tempera command. |
| Artifacts | The closest general capability is `ctx.spillStore.saveText()`: it persists full text and returns an opaque locator, byte count, and retrieval hint. Its own docs say it has no retrieval or deletion API, no retention policy, and no access-control semantics. | Reuse only for diagnostic/oversized textual output where trust-chain identity is unnecessary. DSH Session raw artifacts remain session-log artifacts, not Candidate storage. | The official capability inventory contains no general immutable artifact service with content digest, schema/media identity, `verify(ref, integrity)`, retention ownership, or trustworthy confirmation evidence. Tempera needs a DSH-native artifact binding/verifier service; Candidate, Review evidence, durable proposal payloads, and Operation confirmations cannot rely on a mutable path or `SpillRef`. |
| Sandbox | `ctx.sandboxPolicy.resolve()` produces a per-call mode/root; `ctx.sandbox.confine(argv, policy)` must return enforcing argv or fail closed. Modes cover file effects only. `workspace-write` permits the canonical workspace plus provider temp; enforcement is reported as `full` or `partial`; silent unconfined fallback is forbidden. Network/process visibility is outside the policy. | Reuse for local command confinement after the realizer/provider contract states its required enforcement level. Require `full` when the acceptance test depends on a hard file boundary, and persist the resolved policy summary in execution provenance. | Sandbox policy is not Task `AuthorityScope`, does not freeze Git base/preconditions, and does not cover network/process authority. Different subagent transports may not execute through the same sandbox path. Tempera needs provider conformance tests and must reject unsupported/partial enforcement when policy requires more. |
| Workspace | `ctx.workspaceRegistry` durably maps a generated id to a canonical existing directory and accounts Sessions whose immutable header cwd matches it. It never deletes the directory or Session logs. Create/delete use a pending-mutation marker to recover their own two-write registry update. | Reuse workspace identity/canonicalization where convenient, or bind its id/path into an opaque provider scope outside Task Core. | This is a UI/session grouping registry, not an isolated workspace, Git worktree, Candidate builder, diff snapshot, exact apply, precondition verifier, or effect reconciler. No official Git/worktree Candidate provider was found in the current package/capability inventory. The MVP needs a Tempera-oriented Git/workspace provider that owns these semantics. |
| Provider lifecycle | Cordis disposes dependent consumers when a required service vanishes. Named subagent providers coexist; accepted runs are not revoked merely because a provider registration is removed. DSH's registration APIs return disposers. | Treat provider presence as launch-time availability and provider disappearance as a durable waiting/indeterminate input, never Task failure. Resolve and freeze one binding before creating/launching an Invocation. | No generic DSH API freezes a provider implementation/version/config/capability snapshot or resolves Tempera semantic requirements. Hot reload can race launch. Tempera needs a narrow resolver/registry contract, a stable binding schema, and launch/recovery rules that fail closed when the frozen binding cannot be honored. Dynamic model-authored Cordis plugins are process-local and cleared on DSH restart, so they are not an MVP correctness dependency. |

## Evidence by subsystem

### Cordis and lifecycle

The [Cordis primer](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/cordis-primer.md), [service/dependency guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/user/develop/framework/service.md), and [lifecycle/effects guide](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/cordis-tutorial/02-lifecycle-and-effects.md) establish service injection, pending activation, automatic dependent teardown/reload, reversible registrations, fiber cleanup, and service isolation. Those are strong composition guarantees but contain no durable work or authority semantics.

### Storage

The [storage subsystem contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/storage.md) says a backend unit does not serialize concurrent writes and guarantees atomicity/durability per single call; the domain layer supplies one per-domain write chain and durability-before-memory/event ordering. The normative [`KvUnit` source contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/packages/storage/storage/src/backend.ts) exposes only `loadAll`, `putRecord`, `deleteRecord`, `setGlobal`, and `close`, confirming the absence of a public multi-record transaction. This is sufficient evidence to keep the authority-store decision open while excluding an assumed multi-record transaction that DSH does not promise.

### Execution and subagents

The [jobs contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/jobs.md) explicitly names the shipped registry process-local and ties owned jobs to live Agent cleanup. The [workflow contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/workflow.md) defines a holder-owned live run whose durable chat records may end as an interrupted prefix. The [schedule contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/schedule.md) explicitly documents session-local execution and its at-least-once crash interval.

The [subagent contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/subagent.md) is the strongest reusable execution seam: named providers, fail-loud capability checks, one-shot run/result/disposal, durable continuable child identity, and cold resume. It also explicitly states that a one-shot run is not a durable child handle, remote runs lack durable local enumeration, and provider removal only blocks new starts. These limits require the Tempera fencing/proposal layer above it.

### Artifacts, sandbox, and workspace

The [spill contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/spill.md) is locator-oriented textual spill storage and explicitly lacks retrieval, deletion, retention, and access-control semantics. It does not claim digest verification or immutability.

The [sandbox contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/sandbox.md) gives a useful fail-closed per-call filesystem boundary, while explicitly excluding network/process visibility and distinguishing full from partial enforcement. The [workspace contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.2-alpha.3/docs/subsystems/workspace.md) is a durable canonical-directory/session registry; it states that registry deletion never touches directories, files, live Sessions, or logs. Together they provide identity and confinement, not Candidate/effect semantics.

## Required Tempera-owned MVP seams

The evidence supports four minimum DSH-native additions, all outside Task Core:

1. **Realizer resolver/adapter** — resolves a frozen Stage requirement to a stable `RealizerBinding`; launches through a named DSH provider; returns only a constrained proposal reference/result; supports best-effort cancel and reports capability/provenance. Correctness remains in Tempera generation fencing.
2. **Artifact binding/verifier** — stores or binds immutable content, returns opaque `ref + integrityIdentity`, and verifies the pair. It must cover Candidate artifacts, Review evidence, proposal payloads when durable, and Operation confirmation evidence.
3. **Git Candidate/workspace provider** — creates an isolated realization area, freezes base/preconditions, materializes an immutable Candidate identity/integrity descriptor, and checks target drift before apply.
4. **Authoritative effect provider** — dispatches under a stable `effectKey`, returns confirmed/not-applied/indeterminate, reconciles the same intent, and produces immutable confirmation evidence. It never decides whether dispatch is authorized.

Separately, Tempera runtime needs an **authority persistence service** with one atomic commit covering Task CAS/version, idempotent request result, authoritative current state, and append-only journal addition. This service may be composed through Cordis but is not supplied by Cordis itself.

## Uncertainties that downstream tickets must resolve

- **Storage envelope viability:** `storageDomain.update()` can atomically replace one value on its in-process chain. A prototype must measure and crash-test whether putting the whole Task aggregate, journal, and request ledger in one record is acceptable. Until proven, do not call this a transactional authority store.
- **Cross-process behavior:** current docs promise process-local serialization for jobs/domain coordination, not cross-process CAS. Distributed multi-manager operation is out of MVP scope, but the store must still refuse accidental concurrent writers or document/enforce a single-writer process boundary.
- **Provider provenance:** the generic subagent descriptor has provider name/capabilities and optional route defaults, but no standard provider implementation version/config digest. The RealizerBinding ticket must define what Tempera records and how adapters obtain it.
- **Provider sandbox coverage:** DSH's sandbox contract is strong where a consumer calls it, but not every in-process or external subagent transport is proven to pass all work through `ctx.sandbox`. Conformance tests must establish the actual first provider's boundary.
- **Structured proposal durability:** subagent structured output is a live result. The adapter must decide how it writes the immutable proposal payload before attempting the authoritative accept command, then test the crash between those steps.
- **Release churn:** DSH remains developer preview. Exact package names and method signatures in this audit must be revalidated against the pinned release during ticket “Define the DSH-native service and plugin boundaries”; feature detection cannot substitute for durable semantic versioning.

## Implications for downstream Wayfinder tickets

- **Choose the first transactional persistence boundary:** begin from “no public DSH multi-record transaction.” Compare a proven one-record envelope against a Tempera-owned SQLite transaction; require atomic state + journal + request ledger + Task version and an explicit single-writer/cross-process stance.
- **Define the DSH-native service and plugin boundaries:** reuse Cordis composition and wrap `ctx.subagents`; add the four narrow seams above. Keep `ctx.jobs`, workflow, and Schedule as optional projections/UX, not authority.
- **Define the exact Candidate workspace and effect contract:** assume no existing official Git/worktree or artifact-integrity provider. Specify base/preconditions, digest verification, effect key, dispatch outcomes, reconciliation, and confirmation evidence explicitly.
- **Specify the authoritative transaction and recovery protocol:** derive restart scans solely from Tempera's authority store. DSH job/run/session state may improve reattachment but must never override fencing or authorize a retry.
- **Design the durability conformance harness:** include provider unload/hot-reload during resolve/start, DSH restart with missing jobs, remote-run non-enumerability, partial sandbox enforcement, artifact mutation, proposal-write/accept crash, and effect-dispatch ambiguity.
- **Order and gate the MVP vertical slices:** first prove the authority transaction with fake adapters; then add Cordis composition and a DSH subagent realizer; then artifact/Git Candidate production; finally exact apply plus reconciliation. A successful DSH run is never an acceptance gate by itself.
